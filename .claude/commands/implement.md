プラン `$ARGUMENTS` を実装する。

## 1. 準備

1. プランと、プランに書かれた仕様書、`README.md`、`test/README.md` を読む。`CLAUDE.md`・`docs/` 配下に設計のドキュメントがあれば、それも読む。プランが見つからなければ、`/plan <仕様書のパス>` で先に作るようユーザーに伝えて**ここで止める**。
2. プランや仕様書に、実装方針が変わるほど曖昧な点や矛盾があれば、**実装を始める前に**ユーザーに質問する。推測で埋めない。
3. `git status --short` が空であることを確認する。未コミットの変更がこの仕様書とプランだけなら、`📝 docs: <機能名>の仕様書と実装プランを追加` のようにコミットしてから進む。それ以外の変更があれば止めてユーザーに確認する。
4. 現在のブランチが main なら、止めてユーザーに確認する。
5. `git fetch origin` する（レビューの比較元は `origin/main`）。

このコマンドの中でコミットするときは、`.claude/commands/cmt.md` の「コミットメッセージのルール」に従う（例: 直したときは `🩹 fix:`）。

## 2. タスクの確認

プランの「タスク」をそのまま使う。各タスクの目的、担当範囲、満たすべき要件、公開 API、確かめ方はプランに書かれている。

- プランを書いた後にコードが変わり、担当範囲のファイルがない・公開 API が既にあるなど、プランどおりに進められない場合は、止めてユーザーに確認する。
- 同じ段階のタスクで担当範囲が重なっていたら、止めてユーザーに確認する（並列に実装すると競合するため）。
- どのタスクの担当範囲にも `test/` 配下が入っていないことを確かめる。入っていたら止めてユーザーに確認する。

## 3. 並列実装

段階ごとに、`implementer` サブエージェントを **1 つのメッセージで同時に**起動する。タスクが 1 件だけの段階は、1 つだけ起動する。

- `subagent_type: "implementer"`、`isolation: "worktree"` を指定する。
- サブエージェントは会話の文脈を持たないので、依頼文だけで作業できるように書く: 仕様書とプランのパス、担当タスクの番号・内容と担当範囲、満たすべき要件、作る公開 API と使ってよい公開 API、確かめ方、ベースのコミット SHA（`git rev-parse HEAD`）。
- DB とポートは worktree 間で共有されるので、依頼文で次のように指示する。
  - `npx prisma migrate dev` など DB を変更する操作は、担当範囲に `prisma/` を含むタスクだけが行う。
  - `npm run dev` でサーバを起動したり、`test/` のテストを流したりしない（ポート 3000 と DB を取り合うため。テストは統合後にまとめて行う）。
  - 確かめ方のうち、上の制約で実行できないものは、実行せずに「未確認」と報告する。

全員の完了を待ち、段階ごとに統合（次の 4.）してから次の段階を起動する。

## 4. 統合

1. 各サブエージェントの結果に含まれる worktree のブランチを、作業ブランチに `git merge` する。競合したら、両方の意図を残して解決する。
2. マージしたら `git worktree remove` と `git branch -d` で worktree とブランチを片付ける。
3. `package.json` や `package-lock.json` が変わっていれば `npm install` する。`prisma/schema.prisma` が変わっていれば `npx prisma generate` する。
4. `package.json` の `scripts` にある次のチェックを実行し、エラーがあれば直してコミットする: `typecheck`（無ければ `npx tsc --noEmit`）、`lint`、`format:check`、`build`。scripts に無いものは飛ばし、飛ばしたことを報告に書く。

## 5. テスト

最後の段階を統合したあと、課題の判定用テストを流す。

1. DB を起動する（`docker compose up -d`）。マイグレーションが増えていれば `npx prisma migrate dev` で適用する。
2. `npm run db:seed` を実行する。
3. `npm run dev` をバックグラウンドで起動し、`http://localhost:3000/api/v1` が応答するまで待つ。
4. `test/` で `npm install`（初回のみ）と `npm run test` を実行する。仕様書の要件に添えられたテストファイルが全部通ることを確かめる。他のテストファイルの失敗は、まだ実装していない機能によるものなら報告するだけでよい。
5. 失敗したら、`test/` は直さずに実装側を直してコミットし、4. のチェックからやり直す。
6. 終わったらサーバを止める（DB はそのままでよい）。

## 6. レビュー

`review` コマンドを Skill ツールで実行する（引数に仕様書のパスを渡す）。`api-reviewer`・`code-review`・`security-review` の 3 つでレビューされ、指摘が「確実な問題」と「判断が分かれる指摘」に分けて返ってくる。

確実な問題は直してコミットし、もう一度 4. のチェックと 5. のテストを通す。直したあとの再レビューは 1 回までにする。判断が分かれる指摘は直さずにユーザーに報告する。

## 7. 報告

ユーザーに次を伝える。

- 実装した内容（仕様の要件ごとに対応状況）と、プランから外れたことがあればその理由
- チェックとテストの結果（通らなかったもの、飛ばしたものがあればそれも）
- レビューで直したこと、直さずに残した指摘
- サブエージェントが自分で判断した点
- ユーザーが確認すべきこと（`npm run dev` のあと叩いてみてほしいエンドポイントと `curl` の例、コードで特に見てほしい箇所など）と、問題なければ `/pr` で PR を作れること
