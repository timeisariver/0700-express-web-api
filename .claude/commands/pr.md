作業ブランチから main 向けの PR を作る。PR の分け方・説明文・セルフレビューは Google Engineering Practices（https://github.com/google/eng-practices 、CC BY 3.0）に沿う。原文の社内語（CL、LGTM など）は出力に使わず、PR・approve のように GitHub の言葉に直す。

## 1. 確認

1. 現在のブランチが main なら止めてユーザーに伝える。
2. `git status --short` が空であることを確認する。空でなければ、コミットか stash をするよう（`/cmt` が使える）ユーザーに伝えて**ここで止める**。
3. `gh pr view --json url,state` で、このブランチの PR が既に開いていないか確かめる。開いていれば URL を伝えて止める。
4. 仕様書とプランを決める。`$ARGUMENTS` があればそれを使う。無ければブランチ名 `feature/<slug>` から `_specs/<slug>.md` と `_plans/<slug>.md` を探す。見つからなければ仕様書なしで進める。
5. `git fetch origin` し、`git diff --stat origin/main...HEAD` と `git log --oneline origin/main..HEAD` で、PR に入る変更とコミットを確かめる。

## 2. 変更の大きさを確かめる

PR は 1 つの自己完結した変更にする。`package-lock.json`・`prisma/migrations/` など自動で生成されるファイルを除いて数える。

- 100 行を超えていて、**複数の関心事が混ざっている**場合（例: プロジェクトの土台作りと機能の追加、リファクタリングと機能変更、関係ないリソースの変更）は、どう分けるかの案（どのコミット・ファイルをどの PR にするか）をユーザーに示し、このまま 1 つの PR にするか確認する。
- 100 行を超えていても、1 つの関心事にまとまっていれば（例: 1 つのエンドポイントの model・controller・router）そのまま進む。
- リファクタリングや大きな整形・リネームが機能変更に混ざっていたら、分けることを提案する。

## 3. レビュー

### 3-1. `/review`

`review` コマンドを Skill ツールで実行する（引数に仕様書のパスを渡す）。仕様・バグ・セキュリティの観点の指摘が返ってくる。

### 3-2. セルフレビュー

`git diff origin/main...HEAD` を、レビュアーになったつもりで読み直す。まず全体（1〜2）を見て、致命的な設計の問題があればそこで止めて報告する。問題なければ 3 以降を上から当てる。3-1 と重なる観点（バグ・脆弱性・仕様との違い）は 3-1 の結果を使い、二重に指摘しない。

1. この変更は筋が通っているか。説明文だけ読んで意図が分かり、いま入れるべき変更になっているか。
2. 設計は妥当か。置き場所（router / controller / model / middleware / lib）は正しいか、既存のコードと噛み合うか。
3. 必要以上に複雑になっていないか。仕様書に無い、将来のための先回りの実装（over-engineering）が混ざっていないか。
4. エッジケース（空の一覧、存在しない ID、不正な入力、トークン切れ）とエラーの経路を頭の中で一度通したか。
5. 変更したエンドポイントに対応するテストが `test/` にあり、`/implement` で通っているか。`test/` に無い振る舞いは、PR の本文に確認方法（`curl` の例など）を書いたか。
6. 命名は、中身を見なくても役割が伝わるか。長すぎず、意味を十分に伝える長さか。
7. コメントは「何をしているか」ではなく「なぜそうしたか」を説明しているか。古い TODO やデバッグ用の `console.log` が残っていないか。
8. 周りのコードと書き方が揃っているか。
9. セットアップ・起動・Seed・環境変数の手順に影響するなら、README や `.env.example` を更新したか。
10. 差分の全行を読み、各行が何をしているか説明できるか。

### 3-3. 指摘を振り分ける

3-1 と 3-2 の指摘を次の 2 つに分ける。指摘には理由を添え、命令ではなく何が問題かを書く。

- **blocking**: バグ、設計の欠陥、仕様書の要件を満たしていない、テストが通らない、脆弱性など、マージするとシステムが壊れるもの。3-1 の「確実な問題」はここに入れる。
- **nit**: 好みや軽微な書き方の違い。頭に「Nit:」を付ける。3-1 の「判断が分かれる指摘」は、内容を見てどちらかに振り分ける。

完璧は求めない。blocking が無く、マージすれば全体のコードの健全性が確実に良くなるなら PR を作ってよい。

- **blocking が 1 件以上**あれば、PR は作らずに blocking と nit を分けて伝え、止める。直してから `/pr` をやり直すか、このまま PR を作るかはユーザーが決める。ユーザーがこのまま作ると答えたら、残した blocking を PR の本文に書いて 4. に進む。
- **nit だけ**なら、PR の本文に書いて 4. に進む。

## 4. PR を作る

1. `git push -u origin <ブランチ名>` する。
2. `gh pr create --base main --head <ブランチ名>` で PR を作る。
   - **タイトル**: 何をする PR かが 1 行で分かる短い要約（例: 「タスクの作成 API を追加」）。「修正」「対応」だけのような中身の無いタイトルにしない。
   - **本文**: 次の見出しで書く。「何を」「なぜ」「限界」は、本文だけ読めばレビュアーが意図を分かるように書く。

     ```markdown
     ## 何を
     <この PR で変わること。変更したエンドポイントを含める（例: `POST /api/v1/users/tasks` を追加）>

     ## なぜ
     <背景と目的。仕様書があればその概要>

     ## 限界・トレードオフ
     <対象外にしたこと、プランで判断した点、既知の制約。無ければ「なし」>

     ## 仕様書・プラン
     - _specs/<slug>.md
     - _plans/<slug>.md

     ## 要件
     <仕様書の要件のチェックボックス。実装済みのものにチェックを入れる>

     ## 確認方法
     1. `docker compose up -d`
     2. `npm run db:seed`
     3. `npm run dev`
     4. `test/` で `npm run test`
     <test/ に無い振る舞いがあれば、curl の例を足す>

     ## レビューで残した指摘
     <残した blocking と Nit:。無ければ「なし」>

     🤖 Generated with [Claude Code](https://claude.com/claude-code)
     ```

## 5. 報告

次を伝える。

- PR の URL
- セルフレビューで見つけた良い点（1〜3 個）
- 本文に残した blocking と nit の件数
