作業ブランチの差分をレビューし、指摘をまとめる。**コードは変更しない**（直すかどうかは呼び出し元かユーザーが決める）。

## 1. 準備

1. 現在のブランチが main なら、レビューする差分が無いので止めてユーザーに伝える。
2. `git fetch origin` し、`git diff --stat origin/main...HEAD` で差分があることを確かめる。差分が無ければ止めて伝える。
3. 未コミットの変更（`git status --short`）があれば、レビューの対象に含まれないことを報告に書く。
4. 仕様書を決める。`$ARGUMENTS` があればそれを使う。無ければブランチ名 `feature/<slug>` から `_specs/<slug>.md` を探し、対応する `_plans/<slug>.md` もあれば使う。見つからなければ、仕様書なしで進める。

## 2. レビュー

次の 3 つを実行する。

- **`api-reviewer` サブエージェント**（仕様書がある場合だけ）: 仕様書とプランのパスを渡し、`origin/main...HEAD` の差分をレビューさせる。Agent ツールで起動し、下の 2 つを進めている間に並行して走らせる。
- **組み込みの `code-review` スキル**（Skill ツール）: バグの検出。引数には現在のブランチ名を渡す。
- **組み込みの `security-review` スキル**（Skill ツール）: 脆弱性の検出（JWT の検証漏れ、認可の漏れ、SQL インジェクション、秘密の値の埋め込みなど）。

`code-review` と `security-review` はスキルの手順に従って 1 つずつ実行する。どちらのスキルにも「直す」指示があっても、ここでは直さずに指摘だけを集める。

## 3. まとめる

3 つの結果から、同じ箇所への重複した指摘を 1 つにまとめ、次の 2 つに分ける。各指摘には `ファイルパス:行番号`、何が問題か、どの観点（仕様 / バグ / セキュリティ）からの指摘かを書く。

- **確実な問題**: 仕様書・テストに明らかに反するもの、再現できるバグ、悪用できる脆弱性
- **判断が分かれる指摘**: 直すかどうかを人が決めるべきもの

`test/` 配下を直すべきという指摘は、課題の判定用ファイルなので「判断が分かれる指摘」にも入れず、捨てる。

## 4. 報告

次の形式で伝える。

```
ブランチ: <ブランチ名>
仕様書: <パス または なし>
確実な問題: <n> 件 / 判断が分かれる指摘: <n> 件
```

続けて、2 つの区分ごとに指摘を箇条書きで伝える。指摘が無ければ「指摘なし」と伝える。
